Cada tarefa fixa os **arquivos, interfaces, testes obrigatórios (nomes e asserções) e critérios de aceite**. Antes de iniciar cada marco, o executor **detalha as tarefas daquele marco em passos TDD** (superpowers:writing-plans) em `docs/superpowers/plans/2026-11-23-abby-cash-mN-<nome>.md`, respeitando exatamente as interfaces daqui. Interfaces definidas aqui não podem ser renomeadas sem atualizar este arquivo.

**Objetivo:** Assistente de finanças pessoais e familiares operado por WhatsApp/Telegram (texto, áudio, foto), com painel web PWA, auto-hospedado.

**Arquitetura:** Monorepo com `backend/` (FastAPI + worker ARQ no mesmo pacote Python), `web/` (React PWA) e `infra/` (Docker Compose, Nginx, backups). Canais são adaptadores atrás de uma interface única; webhooks só enfileiram; o worker interpreta (Claude para texto/comprovante, faster-whisper auto-hospedado para áudio), executa regras de domínio e responde.

**Stack:** Python 3.12, FastAPI, SQLAlchemy 2 (async, asyncpg), Alembic, Pydantic v2, ARQ + Redis 7, PostgreSQL 16, `anthropic` SDK, faster-whisper, pytest + pytest-asyncio + testcontainers (ou serviço Postgres no CI), ruff, mypy · React 18 + Vite + TypeScript, TanStack Router/Query, Tailwind + shadcn/ui, Recharts, vite-plugin-pwa, Vitest, Playwright · Docker Compose, Nginx, rclone.

**Spec:** `docs/superpowers/specs/2026-11-23-abby-cash-design.md` (seções 13 e 14 prevalecem).

**Identidade visual:** `docs/design/identidade-visual.md` + `docs/design/logomarca.md` (marca da família Abby, referência abby-map).

## Restrições globais

- Valores monetários **sempre `int` em centavos** (coluna `BIGINT`). Proibido `float` para dinheiro em qualquer camada, inclusive JSON da API (campo `amount_cents`).
- Moeda BRL, idioma pt-BR, fuso padrão `America/Sao_Paulo`; datas de competência (`date`) calculadas **no fuso do usuário**, timestamps em UTC (`timestamptz`).
- Toda tabela financeira tem `space_id`; todo acesso passa por `require_member(session, user_id, space_id)`.
- Segredos só via variáveis de ambiente; `.env` no `.gitignore`; `.env.example` versionado; `gitleaks` no CI.
- Formato de valor nas mensagens: `R$ 1.234,56`.
- Confirmação após todo lançamento via chat: `✅ R$ 45,00 · Alimentação · Mercado · hoje · Conta Nubank` + linha `Responda "corrigir" se errei.`
- Comprovante por foto **nunca** grava sem confirmação explícita.
- Alertas de teto em **80%, 100% e acima de 100%**, uma vez por limiar/escopo/mês.
- Lembretes de conta: **1 dia antes e no dia**, às **09:00** no fuso do usuário (configurável), aviso de atraso no dia seguinte.
- Cadastro **somente por convite**.
- Pagamentos (conta a pagar e fatura) **sempre têm conta de origem** (`checking`/`savings`/`wallet`) e geram lançamento.
- Modelo de IA via env `AI_MODEL` (padrão `claude-opus-5-5`); STT via env `STT_MODEL` (padrão `small`).
- Não alterar nem derrubar o `abby-chat` no servidor compartilhado.
- Commits pequenos, mensagens em inglês no formato Conventional Commits.
- Visual da família Abby: tema claro por padrão (Névoa/Tinta/Vidro/Luz), escuro opcional (`.dark`, chave `abby-tema`), fonte Onest, logomarca `marca.svg` + wordmark `abby cash` em minúsculas, **só tokens** (nunca hex em componente). Fonte da verdade: `docs/design/identidade-visual.md`.

## Foco de revisão

1. **Datas de fechamento de cartão:** compra no próprio dia do fechamento, fechamento dia 31 em fevereiro/abril, compra às 23:30 em `America/Sao_Paulo` (já é outro dia em UTC). Esperado: fatura correta pelo dia local; dia inexistente vira o último dia do mês. → testes em T2.3.
2. **Webhook duplicado** (Evolution/Telegram reenviam): a mesma mensagem nunca gera dois lançamentos. → teste em T3.2.
3. **Formatos de valor** "1.234,56", "1234.56", "R$45", "45 reais", "45,5", "mil e duzentos" (áudio): todos viram o valor certo; valor zero ou negativo é rejeitado com pergunta. → testes em T1.2 e T3.4.
4. **Privacidade em cartão compartilhado:** lançamento `#pessoal` da esposa no cartão do espaço dela, visto pelo marido (só membro da família): aparece apenas agregado em "Outros lançamentos (privados)". Membro removido do espaço perde acesso imediatamente. → testes em T2.2 e T2.3.
5. **"paguei" ambíguo:** sem contas pendentes, com uma, com várias (lista numerada), e resposta "2" escolhendo a segunda. → testes em T5.2.

## M3 — Assistente no Telegram

### T3.1 Interface de canais e adaptador do Telegram
**Arquivos:** `backend/app/channels/{base,registry,telegram,meta_cloud}.py`, `backend/app/api/webhooks.py`.
**Interfaces:**
```python
@dataclass
class InboundMessage:
    channel: str            # "telegram" | "whatsapp_evolution" | "whatsapp_cloud"
    external_message_id: str
    external_user_id: str   # chat_id / telefone E.164
    text: str | None
    media_kind: Literal["audio", "image"] | None
    media_ref: str | None
    received_at: datetime

class ChannelAdapter(Protocol):
    name: str
    async def parse_webhook(self, request: Request) -> list[InboundMessage]: ...
    def verify(self, request: Request) -> bool: ...
    async def send_text(self, external_user_id: str, text: str) -> None: ...
    async def download_media(self, media_ref: str) -> tuple[bytes, str]: ...  # (bytes, mime)
```
`POST /webhooks/{channel}` → `verify` (Telegram: header `X-Telegram-Bot-Api-Secret-Token`) → grava `inbound_messages` (único por `channel+external_message_id`) → enfileira `process_inbound(inbound_id)` → responde 200. `meta_cloud.py` levanta `NotImplementedError`.
**Testes:** `test_telegram_webhook_rejects_bad_secret`, `test_webhook_enqueues_and_returns_200`.

### T3.2 Vínculo de canal e idempotência

### T3.3 Interpretador (Claude) e atalhos
**Arquivos:** `backend/app/ai/{llm,claude_parser,usage}.py`, `backend/app/assistant/{intents,shortcuts,context}.py`, `backend/tests/assistant/eval_cases.yaml`.
**Interfaces:** `ParsedIntent` (Pydantic) com `intent: Literal["lancar_despesa","lancar_receita","lancar_parcelado","corrigir","apagar","pagar_conta","nova_conta_a_pagar","aporte_meta","consultar_gastos","consultar_teto","consultar_saldo","consultar_faturas","ajuda","desconhecido"]` e campos opcionais `amount_cents, description, merchant, category_name, account_hint, card_hint, installments, occurred_on, private (#pessoal), goal_hint, period, confidence: float`. `class IntentParser(Protocol): async def parse(self, text: str, ctx: SpaceContext) -> ParsedIntent`. `ClaudeIntentParser` usa `anthropic.AsyncAnthropic` + `client.messages.parse(...)` com o modelo Pydantic (saída estruturada), `model=settings.AI_MODEL`, effort `low`, data atual e fuso no prompt, e o contexto (categorias, contas, cartões, metas, regras aprendidas) no system prompt com cache. **Consultar o skill `claude-api` antes de escrever esse código.** `try_shortcut(text) -> ParsedIntent | None` cobre `paguei`, `corrigir`, `apagar último`, `saldo`, `teto`, `ajuda` e números isolados para escolha em lista. `record_ai_usage(space_id, kind, input_tokens, output_tokens | seconds)`.
**Testes:** `test_shortcuts_without_llm` e `test_eval_cases` (com parser falso; o conjunto `eval_cases.yaml` tem ≥ 40 mensagens reais em pt-BR com o resultado esperado, inclusive gírias, "#pessoal", parcelado "em 3x", datas "ontem"/"sexta"). Script `scripts/run_eval.py` roda o conjunto contra o Claude real (manual, não no CI).

### T3.4 Orquestração da conversa
**Arquivos:** `backend/app/assistant/{processor,flows,replies,state}.py`, `backend/app/jobs/inbound.py`.
**Interfaces:** `async process_inbound(ctx, inbound_id)`. Pipeline: idempotência → mídia (M6) → atalho ou parser → validação → se faltar valor, ou `confidence < 0.6`, pergunta e salva em `conversation_state` (expira em 30 min) → executa no domínio → resposta de confirmação → checa o teto (M5). Espaço: `#pessoal` → espaço pessoal; `#familia` → espaço familiar; senão `users.default_space_id`. Conta: dica da mensagem → `space_members.default_account_id` → pergunta. Correção da categoria grava `category_rules(space_id, merchant_norm → category_id)`, e as regras têm precedência sobre o LLM. Se o LLM falhar (timeout ou erro): tenta `parse_brl` + resto como descrição, categoria "Outros", e avisa.
**Testes:** `test_expense_message_creates_tx_and_confirms`, `test_private_tag_goes_to_personal_space`, `test_missing_amount_asks_and_resumes`, `test_correction_learns_rule`, `test_llm_failure_fallback`, `test_parcelado_reply_mentions_future_budgets`, `test_zero_amount_rejected`.

### T5.1 Lembretes de contas e geração de recorrências
**Arquivos:** `backend/app/jobs/{scheduler,bills}.py`.
**Interfaces:** cron do ARQ a cada 15 min: envia os lembretes cujo horário local (padrão 09:00, `users.reminder_time`) já passou, para o dia anterior, o dia do vencimento e o atraso (D+1); tabela `bill_reminders_sent(bill_id, kind)`. Destinatário: o responsável ou todos os membros. Job diário gera as ocorrências recorrentes (horizonte de 3 meses) e atualiza o valor das contas espelho de fatura até o fechamento.
**Testes:** `test_reminder_sent_once_day_before_and_due_day`, `test_reminder_respects_user_timezone`, `test_overdue_notice_next_day`.

### T5.2 "paguei" e resolução de ambiguidade
**Arquivos:** `backend/app/assistant/flows/pay.py`.
**Interfaces:** com contexto de lembrete recente (`conversation_state.last_reminded_bill_id`, 24 h), quita aquela conta; sem contexto: 0 pendentes → "Não encontrei contas em aberto"; 1 → quita; várias → lista numerada e aguarda o número. Conta de origem: dica ("no dinheiro" → wallet, "pela conta Itaú") → padrão → pergunta. Para uma fatura, chama `pay_invoice`, com valor total por padrão ou o valor informado ("paguei 500 da fatura").
**Testes:** `test_paguei_after_reminder`, `test_paguei_none_pending`, `test_paguei_multiple_lists_and_choose_2`, `test_paguei_cash_uses_wallet`, `test_partial_invoice_via_chat`.

### T5.3 Alertas de teto, metas e resumo semanal
**Arquivos:** `backend/app/jobs/{budgets,goals,digest}.py`.
**Interfaces:** `evaluate_thresholds` é chamado logo após cada despesa (em M3) e também por um job diário de segurança; alertas para todos os membros, por exemplo `⚠️ Você atingiu 80% do teto de novembro: R$ 2.400,00 de R$ 3.000,00.` Job mensal (dia 1) avisa as metas `behind`. Cada tarefa deste marco inclui testes de componente (Vitest + Testing Library) e um fluxo Playwright. O cliente da API é gerado a partir do OpenAPI (`openapi-typescript`) em `web/src/api/`. A interface é mobile-first, com textos em pt-BR, e segue `docs/design/identidade-visual.md`: menu em trilho no desktop, barra inferior no celular, login no padrão Abby e cores financeiras (receita `success`, teto `primary`/`warning`/`destructive` em 80% e 100%, metas `accent`). Toda tarefa de interface (T1.5 e M7) usa a skill `frontend-design`, sempre subordinada à identidade Abby (tokens, logo e fonte não mudam). ## M8 — Produção

### T8.1 Deploy no servidor compartilhado
**Arquivos:** `infra/docker-compose.prod.yml`, `infra/nginx/abby-cash.conf`, `infra/deploy.md`, `.github/workflows/release.yml` (build e push das imagens no GHCR).
**Regras:** projeto Compose com nome próprio (`abby-cash`), rede própria, **Postgres e Redis próprios** (sem tocar nos do abby-chat) e nenhuma porta pública além do que o Nginx expõe. **Antes de alterar o Nginx**, inspecionar como o abby-chat está servido (Nginx no host ou em contêiner) e adicionar apenas um `server` novo para o subdomínio do abby-cash, com certificado Let's Encrypt. Rodar `nginx -t` antes de recarregar. Migrações Alembic rodam no start da API. Limites de CPU e memória por serviço.
**Aceite:** `https://<subdominio>/health` ok; abby-chat continua respondendo; webhooks do Telegram e da Evolution registrados apontando para `/webhooks/...`.

### T8.2 Backups para o Google Drive
**Arquivos:** `infra/backup/backup.sh`, `infra/backup/restore.md`, serviço `backup` (cron) no Compose.
**Regras:** `pg_dump -Fc` diário às 03:00 + tar dos anexos, compressão e criptografia (`age` ou `gpg`, chave em variável de ambiente), envio com `rclone copy` para o remote `gdrive:abby-cash-backups` (configurado pelo dono com `rclone config`). Retenção local e remota de 7 diários, 4 semanais e 6 mensais. Falha avisa o admin pelo Telegram.
**Aceite:** restauração testada em um banco descartável, com os passos documentados em `restore.md`.
